## TC-ACK-03 缺陷的修复实况（查证结论）

用户问"PPT 里说的 TC-ACK-03 在项目里是怎么修的"，实际查了 git 与代码。

**修复提交：`4e9806f`「First Stage Fix」（2026-09-13 15:17，author: isolated）。**
后续 `37d2c2a`「Update Stage 2」（2026-09-14）保留并扩展了该逻辑。

### 修复前（缺陷代码，位于 `websocket_chat` 发送响应之后）

```python
try:
    ack = await asyncio.wait_for(websocket.receive_json(), timeout=30)
    if ack.get('message_id') == respond_msg['message_id']:
        print(f"[确认送达] 消息ID: {respond_msg['message_id']}")
    else:
        print("ACK不匹配")
except asyncio.TimeoutError:
    print("[未收到ACK] 消息可能没有送达")
```

阻塞式专用读取点：`receive_json()` 无差别取走下一条消息。若用户不发 ACK 而是继续发
业务请求 m2，m2 被这里吞掉，ID 不匹配只打印一句日志、不重放 → m2 永久丢失。

### 修复后（当前 `Connect.py`）

1. `pending_ack_id = None` 初始化在 `while True` 之前（现行约 431 行）
2. ACK 判定上提到主循环开头、JSON 解析之后（现行约 445-452 行）：
   ```python
   if (pending_ack_id is not None
       and message.get('message_id') == pending_ack_id
       and message.get('type') != 'client_query'):
       print(f"[确认送达] 消息ID: {pending_ack_id}")
       pending_ack_id = None
       continue
   ```
3. 发送响应之后只做登记，不再阻塞（现行约 572 行）：`pending_ack_id = respond_msg['message_id']`

核心：把「阻塞拉取 + 事后比对 ID」换成「非阻塞状态标记 + 按消息类型分流」。
第三道条件 `!= 'client_query'` 是关键——保证业务请求永远不会被当成 ACK 消费。

### 顺带一起改掉的

- `37d2c2a` 新增心跳 `heartbeat`/`ping` → 回 `pong`、`canceled_request` → 清 `pending_ack_id`；
  否则这两种控制帧会落到 `INVALID_MSG_TYPE` 弹错误。
- 同批修复里还有 `send_error` 补 `message_id`/`status`/`payload`（否则前端 `isServerMessage` 校验不过，
  错误提示到不了用户）、`process_query` 失败后 `continue`（否则 resp 未绑定再抛 NameError 连发两条错误）。

### 验证证据

`pytest tests/test_websocket_cases.py -k "ack"` → **3 passed**。
`test_tc_ack_03_next_query_is_not_consumed_as_ack` 断言
`[item["message_id"] for item in websocket.sent] == ["m1", "m2"]`。

### 仍存的粗糙点（可作为"消息可靠性仍需优先处理"的依据）

- 帧缺 `type` 且当时没有待确认 ACK 时，`message['type']` 仍会 KeyError → 被外层兜成 `SERVER_ERROR`
- `pending_ack_id` 是单槽位，只跟最近一次响应；无重传、无超时清理
- 业务请求的 `message_id` 恰好等于待确认 ID 时会被当业务处理，`pending_ack_id` 保持陈旧
