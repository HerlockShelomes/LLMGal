## 「前端放不出音频」排查（09:37-10:00）

### 结论：后端完全正常，问题只在前端播放环节

证据（全部实测）：
- `/voices` 接口返回 4 角色映射：`Wendy→Serena / Testificate→Momo /
  Testificate_Boy→Ethan / GirlProgrammer→Maia`，音色目录 24 条。
- 走真实 WebSocket 一轮对话（role=Testificate）：`status=success`，`index=0`，
  生成 `Testificate_0_Stream.wav` 1105964 bytes（09:56），`Records.txt` index 推进到 1。
- 所有语音文件大小正常，无 0 字节；vite dev 对 `/src/assets/voice/...` 返回 200 + `audio/wav`。

### 前端播放逻辑加固（ChatView.playAudio）

1. **去掉 `el.load()`**：`el.src = url` 本身就会触发资源选择算法；额外 `load()` 会把
   `readyState` 打回 `HAVE_NOTHING`，紧随的 `play()` 容易被浏览器**静默拒绝**（无声、无报错）。
2. **不能只等 `canplay`**：事件一旦因任何原因不触发就**永久静默**。改为
   `canplay` / `loadedmetadata` 谁先到谁播，**外加 2 秒超时兜底**强制 `play()`。
3. `playTimer` 与 `playAbort` 一起在 `stopAudio()` 里清除，否则「点停止」2 秒后声音会自己响。
4. 加 `[音频] 准备播放 / play() 触发来源 / 资源加载失败 / play() 被拒绝` 四级诊断日志；
   `play()` 被自动播放策略拒绝时弹 `ElMessage` 提示（此前只有 console.warn，用户看不到）。

### 教训

- **判定"有没有返回内容"别用 `curl -o /dev/null -w %{size_download}`，恒为 0**，
  要 `-o 文件` 再看长度，否则会误判成接口返回空。
- 后台命令 `cd X && cmd &` 里的 `cd` 只作用于后台子 shell，**前台后续命令的 cwd 不变**，
  相对路径会算错。
- 排查"没声音"要分层：后端有没有生成文件 → 文件是否可达 → 前端有没有调用 play →
  play 是否被拒。前三层都验证过，问题才定位到第四层。

### 二次定位（用户反馈 `play() 触发来源=timeout-fallback，readyState=0`）

`readyState=0` = 资源**完全没加载**（1.2 秒内既无 `loadedmetadata` 也无 `error`）。
资源侧已排除：curl 实测 `Testificate_0_Stream.wav` → 200 / 1105964 bytes，
`.mp3` → 200 / 384960 bytes（前 4 字节 `\xff\xf3\xe4\xc4` 是合法 MP3 帧头），带 `?_t=` 同样正常。

**根因：我为了规避「load() 后立刻 play() 被拒」，把 `el.load()` 整个删掉了。**
只赋值 `el.src` 时浏览器可能一直不启动加载，readyState 永远停在 0。

**正确组合是三件事缺一不可**（踩过两次坑，别再改错任何一步）：
1. `el.src = url + 时间戳`（破缓存，后端每轮覆盖同名 wav）
2. `el.load()` —— **必须有**，否则加载不启动
3. 等 `canplay`（或 `loadedmetadata`）再 `play()` —— **必须等**，否则 play() 被静默拒绝
4. 再加 1.2 秒超时兜底 + token 守卫，防止事件不触发时永久静默

诊断日志已加到能一次看清：`src` / `readyState` / `networkState` / `error.code`，
并在 play 后 3 秒复查 `paused` / `currentTime`。前端基线 8 passed，build EXIT=0。

- 用 `AbortController` 的 signal 注册 `canplay` / `error` 监听，换音频时 `abort()` 作废旧回调，

## 「play() 已被接受但没声音」真凶定位（10:00-10:30）—— 同元素过期 play 补刀 pause

用户给的第三条日志是本轮突破口：

```
[音频] play() 来源=timeout-fallback readyState=0 networkState=2
[音频] play() 已被接受，等待数据到达
[音频] 3 秒后复查: paused=true readyState=4 networkState=1 currentTime=0 error=无
```

**`readyState=4` + `error=无` + `paused=true` + `currentTime=0` = 有人调用过 `pause()`**
（不是加载失败、不是自动播放被拒）。而 `pause()` 只有三个来源：`audioBus` 的
`claimPlayback`/`stopAllPlayback`、`stopAudio()`、以及 `playAudio` 里那行守卫。

### 根因（自引入，一行）

```js
el.play().then(() => {
  if (token !== playToken) el.pause()   // ← 同一个 <audio> 元素
})
```

新一轮 `playAudio` 已经让**同一个元素**改播新音频（并 `load()` 把 `currentTime` 归零），
旧的 `play()` promise 因为是在 `readyState=0` 时发起的、被挂住很久，迟到落定时
`token !== playToken` 成立 → 执行 `el.pause()` → **掐掉刚开始播的新语音**。
日志里 `readyState=0` 那一行正是"promise 会被挂住"的必要条件。

**规则：同一个 media 元素上，过期请求一律静默忽略；`pause()` 只会伤到自己人。**

### 一并修掉的三个隐患

1. **`stopAudio()` 不递增 `playToken`**：点「停止」后旧定时器仍自认当前请求 → 声音复活。
   现在 `stopAudio()` 第一件事就是 `playToken++` + 清空全部定时器。
2. **`readyState=0` 就 `play()`**（1.2s 超时兜底的锅）：改为**轮询等到 `readyState>=2` 才播**
   （150ms 一次，最长 8s），彻底不用 `canplay`/`loadedmetadata` 事件——事件不触发就永久静默。
3. **dev 下挑到上一轮的旧 mp3**：`import.meta.glob` 是构建期快照，收不到后端本轮覆盖写的
   `{role}_{index}_Stream.wav`，于是回退到**同名历史 mp3**，听到的和屏幕文字对不上。
   新增 `settings.ts::getAudioUrls()`：dev 下把 `/src/assets/...` 直连路径排第一，
   候选列表按 `error` 事件依次回退；生产仍走 glob。

### 新增的两道保险

- `watchPlaybackHealth`：`play()` 被接受后每秒复查，`paused && currentTime===0` 就重播（最多 4 次）。
- `installPauseProbe`：元素被**外部** `pause()` 时打印调用栈（自己 `stopAudio` 触发的不报），
  下次再出问题一次就能看到真凶。

### 测试

`chatAudio.test.ts` 重写为 3 条：readyState 门控、连续两轮先停后播、
**过期 play 迟到落定时不得 `pause()`**（就是本轮这个 bug 的回归测试）。
前端基线 **9 passed**，`npm run build` EXIT=0。
`SettingsPanel.vue` 的 `<source>` 也改成命令式 `el.src`，与 ChatView 同构。

### 踩坑（工具层，值得记）

**同一个文件在一次工具调用块里发两个 Edit，后写的会覆盖先写的，前者静默丢失。**
本轮 `ChatView.vue` / `SettingsPanel.vue` / `chatAudio.test.ts` 的 import 行各丢一次，
是 `vue-tsc` 报 `Cannot find name` 才发现的（`getAudioUrls is not defined` 同理）。
**改同一文件的多处必须串行发。**

（另：`vitest run` + `npm run build` 串在一条前台命令里会超时被 SIGTERM；分开跑各自 9s / 18s 正常。
后台跑同一条命令更是 9 分钟不结束。是工具层限制，不是项目问题。）

### 补充：自愈看门狗与全局通道的冲突（发现后立即修掉）

`watchPlaybackHealth` 本来是「被按停就重播」，但设置面板的试听音 `claimPlayback()`
抢占通道时也会把对话语音 `pause()` 掉 —— 看门狗会在 1 秒后把对话语音抢回来，
两个声音开始互相抢麦、循环打架。
修法：`audioBus` 新增 `isPlaybackOwner(owner)`，看门狗与暂停探针都先判定
「通道还是不是我的」，不是就安静让位。
`expectedPlaying` 标志同样用于让探针只报「我们自认为在播时」的暂停，避免 `load()` 引发的误报。
`audioBus.test.ts` 增至 6 条，frontend 基线 **10 passed**。

## 第三轮：`play 已被接受` + 连"播放正常"都没有（10:49）

用户给的日志只剩两行，且 `readyState=4`（说明我的轮询改造生效了）：

`watchPlaybackHealth` 的四个分支都会打日志，全都没出现 ⇒ 唯一解释是撞上了那个
**静默 `if (token !== playToken) return`** ⇒ 1 秒内有人调了 `stopAudio()`。

### 已确认不是后端的问题

- `Voice.save_audio_from_bytes` 是**同步写盘**，且在 `Integration.Response_Collection`
  返回前完成（`voice_path = Voice_Generation_through_http(...)` 在 return 之前），

### 高度可疑的真凶：Vite 监视了"后端生成物"目录

`stores/settings.ts` 用 `import.meta.glob(..., { eager: true })` **静态引用**了
`src/assets/voice/**` 与 `src/assets/pictures/**`。后端每写一个新文件，Vite 都判定
该模块失效 → HMR 升级成**整页重载**：

- 正在播的语音被掐掉（`onBeforeUnmount` → `muteAll()`）；
- 控制台被清空 → 用户看到的日志"断在半截"，也解释了为什么 1 秒后的
  `播放正常` 永远不出现；
- 时间线索吻合：`_t`≈10:48:30 而同一槽位文件 mtime = 10:48:36（后端在同一轮里
  重写/重试了同一个槽位），重写瞬间正好能触发一次重载。

**修法**：`vite.config.ts` 加

```ts
server: { watch: { ignored: [..., '**/src/assets/voice/**', '**/src/assets/pictures/**'] } }
```

代价：手工新增到这两个目录的文件不再进 glob 快照（要重启 dev server），
而 dev 下语音本来就走直连磁盘路径，不受影响。
长期建议（未实施）：生成物不该落在 `src/`，应由后端 `StaticFiles` 挂载 `/voice`，
前端配 `VITE_VOICE_BASE`，彻底绕开 Vite 模块图（也一并解决生产构建打不进去的问题）。

## 「点击试听放不出声」debug（用户第三次反馈）

### 结论：`blob:` URL 被拼上了查询串，浏览器查不到该 blob → 永远静默无声

`SettingsPanel.previewVoice` 原写法：

```js
const url = URL.createObjectURL(blob)      // blob:http://127.0.0.1:5173/xxxx-xxxx
el.src = `${url}?_t=${Date.now()}`         // ← 致命：blob URL 是不透明串
```

blob URL 是**按整串**去浏览器内部的 blob 注册表里查的，拼上 `?_t=` 后变成另一个串 → 查不到 →
元素永远进不了加载流程：`readyState` 停在 0、`error` 为 null、没有任何事件 → 只有静默超时。
**破缓存的 `?_t=` 只对 http(s) URL 有意义，对 blob 必须原样使用。**

### 修法（`SettingsPanel.vue`）

- `el.src = previewObjectUrl`（**不拼查询串**），照旧 `el.load()` 后轮询等 `readyState>=2` 再 `play()`。
- 新增 `previewObjectUrl` 记录 + `releasePreviewUrl()`（`revokeObjectURL`），换音色与 `onBeforeUnmount` 时释放。
- 抽出 `playWhenReady(sourceLabel, onTimeout)`：150ms 轮询、5s deadline，超时交给调用方决定。
- 超时兜底 `fallbackToDirect()`：blob 链路失败时回退到 `${API_BASE}/api/voices/preview?voice=...&_t=` 直连地址（http(s)，可安全带时间戳）。
- 区分两类失败：`fetch` 拿不到样本 → 提示「后端未启动」（直连也一样没资源，不兜底）；拿到了但放不出 → 走 blob→direct 兜底。

### 验证

`npx vue-tsc -b` EXIT=0；`npx vite build` → `✓ 1887 modules transformed / built in 28.58s` EXIT=0。
（沙箱 Bash 跑 `npx vite build` 依旧 127 + wsl.exe 黑名单阻断，只能用 PowerShell 工具跑。）

## Mock 模式评审性自查：删掉 `_mode_cache`，并让落盘失败不再谎报成功（18:4x）

用户提问「我这样的 mock 设计是否符合正常软件测试中 mock 版的行为」。评审过程中在**自己的实现**里发现两处真缺陷，当场修掉。

### 缺陷一：`get_mode()` 的进程内缓存与对外说明自相矛盾

原实现 `_mode_cache` 首次读盘后缓存，但注释/交付说明写着「每次调用都重新读盘」。后果：多 worker（`uvicorn --workers N`）、手工编辑 `runtime_mode.json`、另一个进程写入，都会出现**界面显示 mock 而实际接请求的进程仍是 prod**（或反之）。

修法：**删除 `_mode_cache` 与 `reset_mode_cache()`**，`get_mode()` = `_read_mode_file() or _initial_mode`，每次读盘。落盘本就是 tmp + `os.replace` 原子替换，读到的必是完整旧值或新值，成本是几十字节的 read，相对一次 LLM 调用可忽略。

### 缺陷二：落盘失败被吞掉，前端收到「切换成功」

`set_mode()` 原先 `except OSError: logging.exception(...)` 后 `return value`。修法：改抛 `RuntimeError`，`Connect.api_set_mode` 捕获后翻成 **500**（响应体带 `detail` 与真实的 `config.get_mode()`），HTTP 400 仍留给非法取值。

### 配套改动

- `tests/conftest.py::force_prod_mode` 原先 monkeypatch `_mode_cache`（已不存在）→ 改为把 `MODE_PATH` 指到 `tmp_path/runtime_mode.json` + `_initial_mode` 钉 prod（等效"从未切换过"，不依赖内部实现，并保留两条断言）。
- `tests/test_mode_switch_cases.py` 重写为 **TC-MODE-01..13**：`force_mode` 改为真实写文件 + 改 `MODE_PATH`；新增 TC-MODE-02（落盘后再手工改文件，验证 `get_mode()` 仍读文件 = 多进程一致性）、TC-MODE-07（`MODE_PATH` 指到已存在目录使 `os.replace` 必失败 → 断言抛 `RuntimeError` 且模式未变）、TC-MODE-08（REST 层翻 500）。
- 后端 **79 passed**（78 → +1）。

### 真多进程验证（不是"读代码觉得对"）

临时探针起 uvicorn 在 8123，外部进程改 `runtime_mode.json`：

```
初始（文件不存在）        -> prod
REST 切到 mock            -> mock | GET: mock
外部进程改成 prod         -> prod   ← 修复前这里会一直返回 mock
外部进程再改成 mock       -> mock
REST 切回 prod            -> prod
```

收尾：`runtime_mode.json`、`.tmp`、探针脚本与临时日志全部清除，恢复默认正式版。

### 评审结论要点（给用户的口径）

- 整体**符合 mock 的精神**：隔离厂商依赖、返回确定性桩数据、不触发真实调用、不污染 `Records.txt`、模式可跨重启持久化。

## 用户反馈「创建成功后角色图片不显示」（21:xx）

### 根因：`getImageUrl` 只查构建期 glob 快照

```ts
const pictureModules = import.meta.glob('/src/assets/pictures/**/*.{jpg,...}', {eager:true, query:'?url'})
export const getImageUrl = (name, index) =>
  resolveAsset(pictureModules, `/src/assets/pictures/${name}/${name}_${index}.jpg`)  // 收不到 → ''
```

`import.meta.glob` 是**构建期快照**。dev server 启动后才由后端写入的 `pictures/林彻/*.jpg`
（磁盘已确认 8 张齐全：`_original` + 7 情绪）**不在快照里** → 返回空串 →
SettingsPanel 落 `显示失败` 占位符、ChatInput 落 `+`。

**为什么看起来"只管创建之后"**：创建流程的候选图走 `staticUrl('/static/pictures/temp/...')`
（后端 StaticFiles 挂载），从来不走 glob，所以预览一直正常 —— 只有定稿后的立绘走了 glob。

这正是音频那轮修过的同一类 bug（当时只修了 `getAudioUrls`，没顺手检查图片）。

### 修法（前端 3 文件）

- `settings.ts` 抽出 `assetCandidates(modules, relPath)`：**构建期 glob → dev 直连 `/src/assets/...` → `staticUrl('/static/...')`**，
  取不到时返回空数组。`getImageUrls` / `getDescriptionFiles` 基于它；保留单值版 `getImageUrl` / `getDescriptionFile` 兼容旧调用点。
  第三级 `/static` **dev/prod 都必须有** —— 生产构建同样早于角色创建，新角色永远不在产物里。
- 新增组合式函数 `useRoleImage(name, index)`：`candidates` + `cursor`，`watch(..., {immediate:true})` 在角色/情绪变化时重置游标；
  返回 `{url, onError}`。`onError` 走到列表尽头就停在空串（`if (cursor < len) cursor++`，避免空 src 反复触发 error 时计数失控）。
- `SettingsPanel.vue` / `ChatInput.vue` 改用该组合式函数，`<img @error="...">` 逐个回退；
  SettingsPanel 仍在**完全取不到**时 `ElMessage.warning('角色图片缺失')`（`showAvatar` 是死变量，已删）。
- ChatInput 里 `i`（情绪索引）**必须上移到 `useRoleImage` 之前** —— 内部 watch 是 `immediate`，放后面会 TDZ 报错。

**玩法**：输入任意文字回车 → 最多 9000 个粒子聚成字形；鼠标扰动、单击炸开、拖尾流光。

**实现要点**
- 离屏 canvas 画文字 → `getImageData` 按 `alpha > 130` 采样目标点；
  `gap` 自适应 3~9（超过 9000 点就加大间距），粒子尺寸随 gap 缩放，密度感保持一致
- 弹簧 + 阻尼收敛：`v += (t-x)*0.016`、`v *= 0.895`，特征值模长 √0.895 ≈ 0.946/帧
- 绘制按目标 x 位置分 **28 个色相桶**，每桶设一次 `fillStyle` 再批量 `fillRect` ——
  避免逐粒子改 `fillStyle` 的性能坑
- 鼠标斥力半径 130px、单击爆炸半径 180px

**踩坑：无头截图下动画停在早期帧**
第一次用 Edge 无头截图（`--virtual-time-budget=8000`）得到的是**一片弥散噪点**，
看着像"物理公式写错了"。实因 **rAF 在无头环境触发次数远少于预期**，动画没跑够帧。
加 `?still=1` 静态模式（初始化时预热 600 步物理）后重截 → 「有意思」三字清晰成形、
5873 粒子、蓝→紫色相渐变 ✓。**差点去改本来正确的代码。**
