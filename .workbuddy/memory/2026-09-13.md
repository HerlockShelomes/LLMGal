## 二、探针修复的三层依赖（用户问：为什么不按探针直接修）

10 条探针按"修复前置条件"分三层：

- **层 1 · 现在可修（4 条）**——落点全在后端状态逻辑，mock 可完整验证：
  `TC-ACK-03`（`Connect.py:268-273` 无条件 `receive_json` 把下条请求当 ACK 吞掉）、
  `TC-CON-01`（`Integration.py:123,205` + `updateLinks:92` 无锁读改写；并把 URL 覆写成空串）、
  `TC-RES-03`（`Integration.py:125-134` `FileNotFoundError` 分支只读不写回）、
  `TC-EX-01`（`Integration.py:123` `matches[0]` 无匹配直接 IndexError）。
- **层 2 · 须先定前端契约（4 条）**——`TC-WS-08`（`Connect.py:290` `send_error` 不带 `message_id`/`status`）、`TC-CFG-01/02/06`（`Connect.py:239-241` `except` 缺 `continue` → `resp` 未定义 → `NameError` → 外层再发 `SERVER_ERROR`，即"双错误响应"）。修它须同步改 `MessageType.ts:isServerMessage` 与 `ChatView.vue` 监听，而前端无有效测试（缺陷 D44）。
- **层 3 · 属 AI 接入层（2 条）**——`TC-LLM-01`（`Text.py:get_llm_response` 的 system prompt `role`）、`TC-IMG-01`（`Image.py:static_images` + `Integration.py:200`）。用户已明确"AI 接入留待后续指示"；且角色语义只有真实服务能验证，mock 只能证明"传了某个字符串"。

**探针翻转规则（硬性，易踩坑）**：探针断言的是"缺陷值"而非"正确值"，所以**缺陷存在时它才绿**。修一条缺陷 = 源码改动 **+ 同轮把该探针断言从「缺陷值」翻转成「正确值」**，两步必须成对做。只改源码不动断言 → 对应用例变红，极易被误判为回归。

- 例：`TC-WS-08` 现为 `assert not {"message_id","status","payload"} <= error.keys()`，修后须改成 `assert {...} <= error.keys()`；`TC-CON-01` 断言期望值里的 `""` 就是缺陷本身；`TC-LLM-01` 现断言 `role == "assistant"`，正确值是 `"system"`。
- 连带同步四份文档：`tests/test_service_and_state_cases.py`（4 条）、`tests/test_websocket_cases.py`（6 条）、`docs/module1/LLMGal_backend_34_test_cases.md` 的预期行为描述、`LLMGal_测试缺陷报告书.docx` 对应条目状态。
- 另：`TC-RES-03` 的修法需先定语义——Records 缺失时是自动建一份还是受控报错，这决定断言怎么写。

## 三、层 1 + 层 2 修复实施（用户指示：修 8 条，层 3 留待后续）

**结果：34 passed / 0 failed / 0 xfailed，退出码 0，2s 内。覆盖率 57% → 59%（Connect 73%、Integration 86%）。未提交 git。**

### 改了什么

`backend/Connect.py`：
1. **ACK 机制重构**（原 268-276 行）：删掉「发完响应后 `asyncio.wait_for(receive_json(), 30)` 阻塞等 ACK」，改为 `pending_ack_id` 待确认状态 + 在主循环顶部识别回执。判定条件为 `message_id 一致 且 type != 'client_query'`，否则按业务请求处理。这是「下一条请求被当 ACK 吞掉」的根因。
2. **`except` 补 `continue`**（process_query 失败分支）：原先不加 continue，`resp` 未绑定 → 构造响应消息抛 `NameError` → 被外层 except 兜住再发一条 `SERVER_ERROR`，即「一次失败连发两条错误响应」。
3. **`send_error` 补 `message_id` / `status` / `payload`**，签名加 `message_id: str = ""`；各调用点用 `message.get('message_id','')` 传入。**顶层保留 `code`/`message`/`detail` 不动** —— 这是为了不破坏 TC-WS-02/04/05/06/07 对顶层字段的既有断言。

`backend/Integration.py`：
4. **按角色名分片加锁** `_lock_for(roleName)` + `_advance_index_only()` 原子占位。**关键约束：锁只能覆盖「读槽位 + 占位写回」这一短临界区，绝不能罩住 `get_llm_response`** —— TC-CON-01 的 `Barrier(2)` 就在 `get_llm_response` 里，粗粒度锁会让两个线程互相等待而 `BrokenBarrierError`。
5. **占位时 `int(index)` 抛 ValueError 不抛出，延后到原位置**：TC-EX-02 要求非法索引的 ValueError 发生在 llm/tts **之后**，所以占位阶段只能吞掉异常、什么都不写。
6. **`updateLinks` 在角色块或目录缺失时补建**（`makedirs` + 追加最小三行记录），并加了 `i + 2 < len(lines)` 边界保护、`break` 避免多块连改。

`frontend/src/views/ChatView.vue`：
7. 补 `invalid_message` 监听。此前 `WebSocketManager` 对不合契约的消息会 `emit("invalid_message")`，但 ChatView 只注册了 `connected`/`disconnected`/`error`/`message`，这类消息被静默丢弃。

### 语音重叠修复（23:30）

用户报「回复的语音有重叠，同一时刻至少两段在播，不容易复现，似乎和测试脚本相关」。后端已排除：`Integration.py:243` 每轮只调一次 TTS，index 与音频文件名严格对应（返回 `str((index-1)%10)`，生成用的也是这个 index）。

**根因在前端 ChatView 的三套播放机制互相打架**：
```js
watch(currentAudioUrl, () => { audio.pause(); audio.load() }, {immediate:true})
<audio :key="audioKey" @canplay="handleCanPlay">   // canplay 里无条件 play()
```
1. `load()` 会重新触发 `canplay`，`canplay` 里无条件 `play()` → **把刚 pause 的元素又复活**；
2. `:key` 变化销毁旧元素，但**浏览器对「已移出文档的 media element」的 pause 是异步的**，新元素开播时旧元素往往还在发声 → 两段重叠；
3. `immediate:true` 让页面一加载就自动播上次的音频；
4. 页面还有第二个 audio（SettingsPanel 试听音，常驻 DOM），与对话音完全不互斥。
「不容易复现」= 异步时序竞争；「和测试脚本相关」= `smoke_e2e.py` 真实调用 TTS 覆盖 `voice/{role}/{role}_{index}_Stream.wav`，还会触发 Vite 文件监听/HMR 加重时序问题。

**修复**：
- 新建 `frontend/src/utils/audioBus.ts` —— 全局单一发声通道，`claimPlayback()` 抢占时先 pause 上一个；`stopAllPlayback()`。
- ChatView：删掉 `:key` 重建 + `<source>` 动态 src + `@canplay` 自动播 → 改为**常驻单一 `<audio>` 元素 + 命令式 `playAudio(url)`**：先 `pause()`+`currentTime=0`，再 `src=`（带 `_t` 时间戳破缓存，因为后端每轮覆盖同名 wav）、`load()`、`play()`；用 `playToken` 自增令牌让过期异步 play 自我静音。
- 去掉 `currentAudioUrl` 的 watch，**改为响应到达时显式 `playAudio()`** —— 否则 index 与上一轮相同时 watch 不触发，新一轮永远播不出来。
- 「停止生成」「重新生成」「编辑重发」「清空」「组件卸载」全部调用 `stopAllPlayback()`。
- SettingsPanel 试听音也走 `claimPlayback`；顺带去掉 `<source type="audio/mpeg">`（试听素材可能是 wav，硬编码 mp3 会让浏览器直接判定不可播）。
- `settings.ts::getAudioUrl` 增加 dev 兜底：glob 拿不到时回退 `/src/assets/voice/...` 直链（后端新合成的 wav 不在构建期 glob 快照里）。生产仍返回空串。

**踩坑**：`vue-tsc` 的 `noUnusedLocals` 很严格，删变量后必须清干净——本次连带删了 SettingsPanel 的 `audioKey` 后 `watch` 也变成 unused，得从 import 里一并删掉（与之前 `checkRoleOverlap` 同一类问题）。

**验证**：后端 66 passed；前端 `vue-tsc -b && vite build` EXIT=0；vitest 5 passed（新增 `src/_tests_/audioBus.test.ts` 4 条覆盖发声通道）。
