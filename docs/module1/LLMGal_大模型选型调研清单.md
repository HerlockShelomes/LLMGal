## 一、结论摘要：推荐矩阵

| 类别 | 首选（推荐） | 备选（成本/自建） | 特定需求 |
|---|---|---|---|
| **文本回复** | **Claude Sonnet 4.6**（人格一致性 + 1M 上下文 + 官方自动压缩） | **DeepSeek V4 系列**（MIT 开源、1M、性价比最高）；**Kimi K2.6**（长文本天花板） | 国内一站式、与现有火山栈同源 → **豆包 Seed 2.0 Pro**；低延迟实时感 → **Gemini 3.5 Flash** |

## 二、文本回复模型

### 2.1 需求拆解为可打分维度

| 需求原文 | 可验证维度 | 权重 |
|---|---|---|
| 角色扮演能力强 | 长对话中人物性格偏移率、对话风格辨识度 | 30% |
| 性格推理能力强 | 心理动机推断、潜台词理解、情绪因果链 | 20% |
| 上下文存储足够长 | 有效上下文窗口（非"最大宣称值"） | 15% |
| 压缩能力强 | 是否有原生压缩/记忆机制；压缩后的信息保真度 | 20% |
| （项目隐含）中文表达 | 中文文风自然度、二次元语感 | 15% |

**关键提醒**："上下文长"与"压缩强"是两件事。**证据**：Anthropic 官方文档明确记录 *context rot*（上下文越长，准确率与召回率越下降），并称"900k token 的提示词并不自动优于精心挑选的 90k"。所以选型时应优先看**有没有服务端压缩机制**，而不是看窗口数字。

### 2.2 候选池与对比

| 模型 | 有效上下文 | 压缩 / 记忆机制 | 角色扮演与人格表现 | 成本（输入/输出 每百万 token） | 接入便利性（本项目视角） |
|---|---|---|---|---|---|
| **Claude Sonnet 4.6** | 200K（可切 1M） | ★ **原生 compaction**（`compact-2026-01-12` beta，按 `input_tokens` 阈值自动摘要）+ context editing（定向清理旧工具结果） | 第三方多源评测一致给出**人物一致性最高分**（30 次场景切换后性格偏移率约 6%，风格辨识度 >90%） | $3 / $15 | 需中转站或海外直连 |
| **Claude Opus 4.7** | 更长（万亿级宣称） | 同上 | 叙事一致性最强，但价格显著更高 | $12+ | 同上 |
| **DeepSeek V4-Pro / V4-Flash** | 1M | 无官方自动压缩，需自建 | 世界逻辑一致性、长程因果强；情感细腻度弱于 Claude | ★ 极低（约 $0.4/M 量级）；火山侧豆包同族推理输入 6 元/百万 token | **MIT 开源可私有化**，国内直连 |
| **Kimi K2.6** | 128K–2M | 无官方自动压缩；超长文本是主打 | 多轮对话与持续演化的关系型对话表现好 | 约 $0.14 / $0.55（Kimi K2 档） | 国内直连，OpenAI 兼容 |
| **Qwen 3.6 / 3.7 系列** | 1M | 无 | 多语言角色扮演最均衡，创意即兴能力强 | 中低 | 国内直连，开源可私有化 |
| **豆包 Seed 2.0 Pro** | 128K | 无 | 中文理解与 C 端对话体验最好之一 | ★ 豆包大模型 Evolving：输入 6 元 / 输出 30 元 每百万 token | **与现有图片/TTS 同属火山方舟，AK/SK 可复用，接入成本最低** |
| **Gemini 3.5 Flash** | 128K–1M | 无 | 速度快、实时感强；深度叙事弱于 Claude | ★ 约 $1.5/M 量级 | 需海外直连 |
| **Gemini 3 Pro** | 1M–2M | 无 | 超长会话不截断 | 中高 | 同上 |
| **GPT-5.x** | 1M | 无 | **指令遵循最可靠** —— 如果你写了一份详细人设 brief，它最能"照做" | $5/M 量级 | 需中转站 |
| **MiniMax M2.7** | 200K | 无 | 出身于角色扮演/陪伴产品，情感陪伴场景专门优化 | 约 $0.3/M 量级（最低价档） | 国内直连 |

### 2.3 推荐清单

**主选 A —— 角色扮演质量优先：Claude Sonnet 4.6**
理由：唯一同时具备"人物一致性评测第一梯队"与"服务端原生压缩"两项能力的候选，直接命中"角色扮演 + 性格推理 + 长上下文 + 压缩"四条需求。`context_management` 可在 15 万 token 阈值自动摘要，会话可无限延续而不需要自建摘要器。

**主选 B —— 国内直连 / 成本优先：DeepSeek V4 系列**
理由：MIT 协议、1M 上下文、价格是 Claude 的百分之一量级，且可私有化（人设与对话数据不出域）。情绪细腻度是短板，但"性格推理"（动机、因果）表现强。**代价**：压缩机制需自建（见第 5 章）。

**主选 C —— 与现有火山栈同源：豆包 Seed 2.0 Pro**
理由：本项目已有火山 AK/SK、TTS 也在火山。文本换到方舟可做到"一份凭据管三类模型"，工程成本最低。适合作为 MVP 阶段的默认模型。

**备选与降级策略（建议实际采用路由策略而非单模型）**

| 场景 | 模型 |
|---|---|
| 主对话（默认） | Claude Sonnet 4.6 或 豆包 Seed 2.0 Pro |
| 高并发 / 实时感要求高 | Gemini 3.5 Flash 或 MiniMax M2.7 |
| 上下文摘要器（压缩用） | 便宜档模型（DeepSeek V4-Flash / Kimi K2），**不要用旗舰模型做摘要** |
| 离线 / 数据不出域 | DeepSeek V4 开源 或 Qwen 3.6 开源，自部署 |
| 需要"照做人设 brief" | GPT-5.x（指令遵循最可靠） |

### 2.4 与本项目的接入点

- `Text.py:38` → 替换 `api_key` / `base_url` / `model` 三处即可，接口本身已是 OpenAI 兼容。
- **必须先修 N02**：`Text.py:34` 现在是 `{"role": "assistant", "content": role_pro}`，角色设定必须改成 `system`，否则换任何模型都拿不到完整人格约束。
- **必须先补上下文层**（第 5 章），否则再长的窗口也用不上。

## 三、语音生成模型

### 3.1 需求拆解

| 需求原文 | 可验证维度 |
|---|---|
| 语音语调、情感色彩仿真强 | 是否有情感控制（枚举式 / 自然语言指令式）、韵律自然度、气口与语气词 |
| 支持音色复制 | 声音克隆的最短参考音频时长、相似度、是否支持零样本跨语种 |

### 3.2 候选池与对比

| 方案 | 情感控制 | 音色复制 | 首包延迟 | 价格 | 中文表现 |
|---|---|---|---|---|---|
| ★ **火山引擎 豆包语音合成 2.0 / 声音复刻 2.0（Doubao-Seed-TTS 2.0 / ICL 2.0）** | ★ **自然语言指令式**（`<整体情绪:生气,语气:吵架,语速:快>`，或句中 `[急切而发颤]`）+ 自动情感理解 | ★ **5 秒级克隆，平均相似度 97.5%** | ★ 流式 300–400ms | 约 1.3 元/千字；音色 150 元/年（企业档） | 中文自然度 9/10，**国内生产环境主力** |
| **MiniMax Speech 2.6（海螺）** | 情绪枚举（喜/悲/怒等）+ 预置音色 100+ | 30 秒音色复刻；**注意克隆能力主要在海外版** | 端到端 < 250ms | 低 | 中文情感成熟，擅粤语等方言与带呼吸感长文本 |
| **IndexTTS2**（B 站开源） | 中文情绪还原**口碑第一**（多平台一致：WER 0.82% 全场最低） | 支持；音色相似度高 | 自部署 | **免费**（算力自担） | 短板：语速偏快、停顿不能精控 |
| **CosyVoice 2/3**（阿里开源） | 情感中等，跨源分歧大（demo 自然度高、长内容被实战派挑刺） | 支持 | 自部署 / 百炼 API | 低（有免费额度） | 中文商用级稳定，生态最好 |
| **Fish Audio S2 Pro** | 可插入笑声哭声等语气 | 开源超写实克隆 + 云 | — | 中低 | 海外盲测中文第一（8.11），**二次元/日配/翻唱强**；短板：单次输入偏短 |
| **Azure TTS** | SSML + speaking style（耳语/喊叫/播报） | 支持 | ★ ~120ms（国内节点） | ★ 约 0.10 元/千字，**50 万字符/月免费** | 韵律最像真人之一，但纯中文情感不如豆包 2.0 |
| **ElevenLabs（Flash v2.5 / Turbo v2.5）** | ★ `[laugh]` / `[whisper]` 情感标签，英文天花板 | 专业级 | 450ms+（国内需代理） | 约 2.1 元/千字 | **中文带英文口音、多音字与方言是短板** → 本项目不推荐 |
| **VoxCPM**（清华开源） | — | ★ 无需参考音频的**"声音设计"**：用文字描述生成全新音色 | 自部署 | 免费 | 适合"原创虚拟角色音色" |

### 3.3 推荐清单

**首选：火山引擎 豆包语音合成 2.0 + 声音复刻 2.0（继续留在火山）**
四条理由：
1. 本项目 `Voice.py` 已在用火山 TTS，`appid`/`token`/`voice_type` 结构不变，**只需升级模型与参数**（把 `enable_emotion` + `emotion` 枚举换成官方 2.0 的 `context_texts` 自然语言指令）。
2. 情感控制从"7 个枚举值"升级为"自然语言指令"——**当前的 `Integration.py:103-127` 里有一半情绪被映射成 `neutral`**（高兴/生气/惊喜/害羞全部落到 neutral），这是明显的表现力浪费，升级后可直接修复。
3. 5 秒克隆 + 97.5% 相似度，满足"音色复制"。
4. 国内直连、SDK 完善、延迟 300–400ms 稳定。

**官方最佳实践要点**（★ 来自火山官方《声音复刻 2.0 最佳实践》）：克隆参考音频建议 **14–30 秒、wav、单声道、低噪声、情绪一致**；超过 30 秒会被自动截断并可能保留瑕疵；降噪会损失一定相似度，需权衡。`context_texts` 还可以传入**上一轮用户 query**，让合成语音与对话语境更贴合——这条对本项目价值很高。

**备选（成本 / 自建）：IndexTTS2**
中文情感还原目前口碑最强、且完全免费自部署，适合"想在语音上做差异化、且愿意承担 GPU 与调参成本"的阶段。短板是语速/停顿不可精控，需要后处理。

**特定需求配对**

| 需求 | 方案 |
|---|---|
| 原创、无真人参考的虚拟角色音色 | VoxCPM（文字描述生成音色） |
| 二次元角色 / 翻唱 / AI 唱歌 | Fish Audio S2 Pro |
| 英文配音为主 | ElevenLabs |
| 极致低延迟 + 免费额度 | Azure TTS（国内节点 120ms、50 万字符/月） |

### 3.4 与本项目的接入点

- `Voice.py:17-20`（`appid`/`token`/`cluster`/`host`）、`Voice.py:79-82`（`voice_type`/`enable_emotion`/`emotion`/`emotion_scale`）。
- 升级后需**同时修 N04**：现在 `Integration.py:231` 把 LLM 的**原始完整回复**（含情绪括号）直接送进 TTS，用户会听到"（高兴）（因为受到朋友的邀请）"被朗读出来。任何语音升级之前必须先剔除标签。
- `Integration.py:103-127` 的情绪映射表应随之重写（补英文情绪词、不要再把 4 种情绪压成 neutral）。

## 四、图像生成模型

### 4.1 需求拆解

| 需求原文 | 可验证维度 |
|---|---|
| 风格保持强 | 同一角色跨多张图的身份保真度（脸、发型、辨识性特征） |
| 人物动作/表情绘制强 | 换姿势、换视角、换表情时的结构正确性（手部、侧后视角） |

本项目额外约束：**日系动漫风格**（`Image.py:96` 写死 `Japanese anime style`）、头像级构图、需要"改表情但脸不能变"。

### 4.2 为什么现状是瓶颈（不是模型不够贵，是范式不对）

当前做法是"**纯提示词描述一致性**"：`Image.py:152-153` 用文字写 `Maintain the image style as well as all the features of the person in this image`，把最近一张图的 URL 作为参考图（`image_urls: [imaurl]`），分辨率 512×512。

这条路径的三个结构性弱点：
1. **没有身份锁定机制**，一致性完全依赖模型"读得懂这句英文指令"；
2. **`Recent_Url` 会被清空**（缺陷 B07）→ 参考图丢失后退化成文生图，角色形象每次漂移；
3. **没有多参考图**，无法把"角色设定图 + 表情参考 + 风格参考"一起喂进去。

### 4.3 候选池与对比

| 模型 | 身份 / 风格保持 | 多参考图 | 分辨率 | 价格 | 备注 |
|---|---|---|---|---|---|
| ★ **豆包 Seedream 4.0 / 4.5 / 5.0** | 4.5 起引入**身份保持系统**（面部特征、发型、光照、整体气质） | ★ 最多 6 张参考图、最多 9 张一致图 | 原生 1K–4K | ★ **5.0：0.22 元/张；4.5：0.25 元/张；4.0：0.20 元/张**（火山官方） | 统一"生成 + 编辑"架构；中英文字渲染强；**与现有火山栈同源** |
| **Nano Banana Pro**（= Gemini 3 Pro Image） | **实测身份保真最强** | 支持多参考（Pro/2 档最多 1–20 张输入） | 1K/2K/4K | 最贵档 | 第三方实测（2026-07-13，同一张参考图、零训练、13 张图手工评分）：**Pro 4.8/5** |
| **Nano Banana 2** | 接近 Pro | 同上 | 1K/2K/4K | 约 Pro 的一半 | 实测 4.3/5，**性价比档**，速度快 |

| **FLUX.1 Kontext Pro** | "**只改 X、其余全保留**"最强（单参考 + 单指令） | 单参考 | — | 中 | 适合"把和服改成校服"这类外科手术式局部编辑；不适合批量 |
| **Qwen-Image-Edit 2511**（阿里开源） | 开源编辑第一梯队，指令遵循可靠、成本低 | 支持 | — | 自部署免费 | 可 LoRA 定制 |
| **HunyuanImage 3.0**（腾讯开源） | **亚洲面孔与动漫风格强**，姿态理解好 | 支持 | — | 自部署免费 | 皮肤纹理略逊 Seedream |
| **Z-Image Turbo**（阿里开源） | 亚秒级出图 | — | — | 免费 | **6GB 显存可跑**，Apache-2.0 |
| **SDXL 家族 + Civitai LoRA** | **二次元/动漫生态无可替代** | 靠 ControlNet / IP-Adapter | 8GB 起 | 免费 | 动漫风格 LoRA 数量与质量没有对手 |

**实测数据出处**：`tinytiny.tools`，2026-07-13，用同一个角色（铜红卷发 + 绿眼 + 雀斑 + 左眉小疤 + 芥末色灯芯绒外套 + 银叶吊坠）的**单张参考图、零 LoRA 训练**，测三个压力场景（咖啡馆大笑/雨夜雨衣/森林中回头）。结论：四款模型在大属性上都好，"微细节最先丢"（那颗小疤最先消失），**即使冠军也只有 4.8/5**——所以工程上应把角色设计建在**醒目、可命名的特征**上。

### 4.4 推荐清单

**首选：豆包 Seedream 4.5 / 5.0（火山方舟）**
理由：与现有 `Image.py` 同属火山生态（`ACCESS`/`SECRET` 已配置）、单价 0.20–0.25 元/张、原生 2K–4K（当前是 512×512）、4.5 起有身份保持系统、支持多参考图、中英文渲染强。**单位成本与迁移成本双低，收益最大。**

**身份/表情精控首选：Nano Banana Pro（Gemini 3 Pro Image）**
当"必须换表情但脸一个字都不能变"时用它；日常批量用 Seedream 控成本。这是官方/第三方都推荐的"用便宜模型跑量、用贵模型定稿"组合。

**局部精修：FLUX.1 Kontext Pro**（或本地跑 FLUX.2 klein）
"保持一切，只改 X"的场景（换服装、改背景、加/去配饰）。

**二次元风格底座：SDXL + Civitai LoRA（ComfyUI 自建）**
本项目是日系动漫风格头像且需要长期稳定同一画风，**LoRA 微调是唯一能真正"锁死画风"的手段**，商业 API 只能做到"接近"。若团队有 GPU（用户在 8703/8700 上有 4×3090 / 8×4090），这条路值得投入。

**开源可控替代：Qwen-Image-Edit 2511**（编辑）/ **HunyuanImage 3.0**（亚洲面孔与动漫）

### 4.5 风格保持的工程手段（模型之外的必做项）

第三方实测给出的四段式提示词结构，**建议直接写进 `Image.py` 的 prompt 模板**：

```
1. 身份锚点（Identity anchor）—— 固定不变的写法，每次都逐字相同：
   "Wendy，银色长发、紫瞳、左耳黑色蝴蝶夹、深蓝水手服"
2. 场景（Scene）—— 只描述这一次的画面
3. 构图（Composition）—— 镜头类型与角度
4. 一致性锁（Consistency lock）—— 显式指令：
   "保持面部特征、发型与辨识性特征与参考图完全一致，只改变场景与姿势"
```

配套：**修好 B07**（`static_images` 不得返回 `""` 清空 `Recent_Url`）——否则参考图链条一断，任何模型的一致性都会崩。

## 六、接入前的强制前置项（否则换模型也不会变好）

按依赖顺序排列：

1. **修 N02** —— `Text.py:34` 角色设定改 `role: "system"`。**这是"角色扮演强"能否兑现的前提**；不修则任何文本模型的人格约束都只有一半效力。
2. **修 N04** —— TTS 输入剔除情绪括号。**不修则语音模型越好，越忠实地念出"（高兴）（因为受到朋友的邀请）"。**
3. **补上下文层**（详见《现存缺陷与修复流程清单》第 5 章）——会话存储 + 上下文组装 + 压缩策略 + 真实 token 统计。当前项目**零多轮记忆**，长窗口模型完全用不上。
4. **修 B07** —— `Recent_Url` 不得被空值覆盖。参考图链条是图像一致性方案的根基。
5. **修 B01** —— 全部密钥迁 `.env` 并轮换。新接的每一家厂商都会再加一份凭据，必须先把密钥管理方式定下来。
6. **修 B03** —— 事件循环阻塞。三家模型都会引入新的同步网络调用，不修则并发数一超过 1 就整体假死。
7. **修 B02** —— 接口鉴权。**在接付费 API 之前必须做完**，否则 `/ws/chat` 无鉴权 + `0.0.0.0` 监听等于把付费额度暴露在网络上。
8. **修 011** —— `pytest.ini` 加 `testpaths`。接了付费 API 之后，"裸跑 pytest 触发真实计费"的风险从"偶然"升级为"必然"。

## 七、风险与决策建议

| 风险 | 说明 | 建议 |
|---|---|---|
| 数据时效 | 模型迭代已达周级（GPT-5.5→5.6 仅三周等），本文价格与型号在采购时可能已变 | 建立季度复评机制；把模型名与价格抽成配置项，不在代码里硬编码 |
| 来源质量 | 部分对比数据来自第三方评测与 SEO 内容，结论可能被厂商营销影响 | ★ 标记项以官方文档为准；角色一致性等主观维度**必须自建小样本评测集**（本项目已有 4 个角色可作测试集） |
| 合规 | 音色克隆涉及真人声音授权；日系动漫风格与角色形象需注意版权 | 克隆音色需取得授权；角色资产建议自制 |
| 供应商锁定 | 深度绑定单一厂商后议价能力下降 | 文本与语音抽象成 Provider 接口（`MultimodalAdapter` 的思路在 `Integration.py:57-83` 已被注释掉，可以捡回来用） |
| 单模型打天下 | 评测一致结论：不同模型在不同任务上各有千秋 | 采用**路由策略**：简单任务走便宜模型，复杂/关键任务走强模型；摘要器用便宜档 |

**最终建议**：MVP 阶段全量走火山方舟（文本 + 语音 + 图像一处凭据、一份账单），把工程复杂度压到最低；同时把 Provider 层抽象出来，等有了真实用户数据和自建评测集，再把文本切到 Claude Sonnet 4.6、把图像定稿切到 Nano Banana Pro。**不要在没有上下文层的前提下先买最长窗口的模型——那是花钱买用不到的能力。**
